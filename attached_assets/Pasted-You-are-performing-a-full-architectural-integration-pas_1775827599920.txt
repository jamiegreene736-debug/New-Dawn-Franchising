CENTRAL EVENT BUS — /core/event-bus.js
─────────────────────────────────────────

A singleton internal event emitter. No system calls another system's functions directly. Everything is decoupled through named events. Use Node's built-in EventEmitter. Do NOT use an external message broker.

Register the following events and their listeners:

seo:task:completed { taskId, taskName, cadence, completedAt, results }
  → Email Digest: adds to today's completed list
  → Content Engine: triggers draft generation if task is content_gap_analysis or keyword_trend_report
  → Weekly Brief: marks data as available

seo:task:failed { taskId, taskName, error, failedAt }
  → Email Digest: adds to issues list
  → Portal: sets red notification dot
  → Weekly Brief: logs for warnings section

lead:created { leadId, name, company, category, score, source }
  → Sequence engine: checks auto-enrolment
  → Portal: activity feed notification
  → Weekly Brief: increments new leads counter

lead:replied { leadId, channel, replyText, repliedAt }
  → Intent classifier: classifies reply
  → Sequence engine: pauses sequence
  → Portal: flags for human review
  → Jamie alert: immediate email notification

lead:intent:positive { leadId, replyText, classifiedAt }
  → Calendly integration: sends booking link
  → Weekly Brief: increments positive replies counter

lead:intent:objection { leadId, objectionType, replyText }
  → Sequence engine: injects objection-handling response
  → Portal: flags objection type

lead:opted_out { leadId, channel, timestamp }
  → Sequence engine: hard stops all sequences immediately
  → Leads table: sets opted_out = true
  → All channel queues: purges pending sends for this lead

visitor:high_intent { fingerprint, pageUrl, visitCount, sessionId }
  → Visitor watchlist: adds or updates entry
  → Portal: visitor intelligence notification
  → Weekly Brief: increments watchlist counter

visitor:identified { leadId, fingerprint, sessionHistory, identifiedVia }
  → Lead gen agent: upgrades lead status and sequence priority
  → Jamie alert: immediate email if lead is a confirmed partner
  → Weekly Brief: logs as notable event

meeting:booked { meetingId, leadId, scheduledAt, calendlyEventId }
  → Meetings system: creates meeting record
  → Calendar integration: creates Google Calendar event for Jamie
  → Jamie alert: immediate booking notification email
  → Brief scheduler: queues pre-meeting intelligence brief for 24 hours before
  → Weekly Brief: increments meetings booked counter
  → Campaign metrics: logs as conversion event

meeting:cancelled { meetingId, leadId, cancelledAt }
  → Meetings system: updates status
  → Sequence engine: re-injects lead into outreach
  → Jamie alert: cancellation notification

content:draft:created { draftId, title, targetKeyword, triggerSource }
  → Portal: shows new draft card in Content Engine panel
  → Weekly Brief: increments pending drafts counter

UNIFIED JOB SCHEDULER — /core/scheduler.js
─────────────────────────────────────────

The ONLY file where cron jobs are registered. No cron jobs may be registered anywhere else. This prevents duplicate registration on server restart.

All jobs must follow this pattern:
cron.schedule(expression, async () => {
  const job = await JobRunner.start(jobName);
  try {
    const results = await jobHandler();
    await JobRunner.complete(job.id, results);
    eventBus.emit('seo:task:completed', { taskId: job.id, taskName: jobName, results });
  } catch (error) {
    await JobRunner.fail(job.id, error);
    eventBus.emit('seo:task:failed', { taskId: job.id, taskName: jobName, error });
  }
}, { timezone: 'America/Chicago' });

UNIFIED EMAIL QUEUE — /core/email-queue.js
─────────────────────────────────────────

All email sends across the entire portal must go through this queue. No module calls nodemailer directly. Search the entire codebase and replace every direct SMTP call with emailQueue.add().

Queue behaviour:
- Max 10 concurrent sends, 200ms minimum delay between sends
- Priority levels: CRITICAL > HIGH > NORMAL > LOW
- 3 retry attempts with exponential backoff: 1min, 5min, 15min
- Dead letter queue for failed sends — log in email_log and notify Jamie via fallback

API: emailQueue.add({ to, from, subject, html, text, priority, metadata })

Monitors who visits www.newdawnfranchising.com, identifies warm visitors, and automatically routes them into the lead gen agent's outreach pipeline.

─────────────────────────────────────────
TRACKING SETUP
─────────────────────────────────────────

Generate a lightweight first-party tracking script to be installed on newdawnfranchising.com. The script captures: page visited, time on page, referral source, return visitor status, UTM parameters.

All visit events write to visitor_events table via a 500ms debounce write queue per session — never flood the connection pool during concurrent SEO jobs.

HIGH-INTENT PAGES — treat visits to these as warm signals and trigger identification logic immediately:
- /fdd, /investment, /contact, /how-it-works, any page with a form submission

─────────────────────────────────────────
VISITOR IDENTIFICATION — THREE METHODS
─────────────────────────────────────────

METHOD 1 — FORM SUBMISSION: Visitor submits any site form → capture name and email → create or match lead record → link session history → route to warm outreach sequence → emit visitor:identified event.

METHOD 2 — EMAIL LINK CLICK: Lead in outreach pipeline clicks a tracked link → session identified automatically → update lead record with visit data → adjust sequence priority → emit visitor:identified event.

METHOD 3 — RETURN VISITOR SCORING: Unidentified visitor returns to high-intent pages 2+ times within 7 days → flag as HIGH INTENT → add to visitor_watchlist → emit visitor:high_intent event. If they ever identify, immediately emit visitor:identified and route to top of outreach queue.

─────────────────────────────────────────
AUTOMATIC OUTREACH ROUTING (via event bus)
─────────────────────────────────────────

On visitor:identified event, the lead gen agent's sequence engine applies this routing logic automatically:
- Lead status NEW: Upgrade to ACTIVE, move to Step 1 of warm sequence
- Lead ACTIVE with sequence running: Inject personalised touchpoint referencing site visit
- Lead NURTURE (gone cold): Resurrect immediately with re-engagement message referencing return visit
- Lead confirmed PARTNER: Emit Jamie alert via email queue immediately

WARM OUTREACH SEQUENCE (separate from cold — triggered by visitor:identified event):
Day 0 — Email: "Saw you were exploring our investment overview — happy to answer any questions"
Day 1 — SMS: Short, friendly check-in
Day 3 — Email: FDD offer with direct download or request link
Day 6 — WhatsApp: Template message with Calendly booking link
Day 10 — Email: Final follow-up with social proof angle

BUILD 3 — CALENDLY MEETING BOOKING INTEGRATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When a lead replies with positive intent, the agent automatically sends a booking link. When they book, everything is logged, Jamie's calendar is updated, and she receives a pre-meeting intelligence brief 24 hours before.

─────────────────────────────────────────
REPLY INTENT DETECTION
─────────────────────────────────────────

When a lead replies to any outreach message, classify the reply via AI into one of:

POSITIVE: Interested, asking questions, wants to learn more → emit lead:intent:positive → Calendly booking flow triggered automatically via event bus
NEUTRAL: Clarifying question → informational response first, then booking flow after 1 follow-up
OBJECTION: Concern or hesitation → emit lead:intent:objection → objection-handling response auto-generated tailored to concern type (cost, visa eligibility, location, operational involvement), then re-offer booking
UNSUBSCRIBE: Wants to opt out → emit lead:opted_out immediately → sequence hard stopped → polite confirmation sent
OUT OF OFFICE: Auto-reply detected → pause sequence 5 business days then resume

─────────────────────────────────────────
CALENDLY INTEGRATION
─────────────────────────────────────────

Connect via Calendly API (CALENDLY_API_KEY, CALENDLY_EVENT_TYPE_URI in .env).

On meeting:booked event (from Calendly webhook → event bus):
1. Create meeting record in meetings table
2. Update lead status to MEETING_BOOKED
3. Log conversion in campaign_metrics via event bus
4. Send Jamie booking notification via emailQueue (CRITICAL priority): lead name, company, category, meeting date/time, which campaign drove the booking, link to lead profile
5. Send lead a confirmation email via emailQueue: meeting details, one-paragraph primer on New Dawn Franchising, link to newdawnfranchising.com
6. Create Google Calendar event for Jamie via Google Calendar API
7. Queue pre-meeting intelligence brief for 24 hours before the meeting
8. Send Jamie a reminder 1 hour before via emailQueue with full lead profile summary

On meeting:cancelled event:
- Update meetings table
- Emit meeting:cancelled to event bus
- Re-inject lead into outreach sequence
- Notify Jamie via emailQueue immediately

─────────────────────────────────────────
PRE-MEETING INTELLIGENCE BRIEF
─────────────────────────────────────────

Triggered: 24 hours before every booked meeting (scheduled via cron entry added to /core/scheduler.js at booking time).

Brief contains:
- Lead's full name, title, company, contact details
- Referral category and lead score
- Which campaign reached them, which step they responded to, what they said
- Website visit history (pages viewed, time on site, visits count)
- Publicly available information about their firm
- Suggested talking points tailored to their referral partner category
- E-2 visa objections most common to their category and suggested responses
